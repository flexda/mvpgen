- 같은 minor 지적이 실행마다 반복된다. 기록(`lessons.md`)은 major만 쌓으므로 이 반복은 줄지 않는다(ARCHIVE에도 같은 문제로 적혀 있다).

## 5. 검증 범위 밖이었던 것

| 확인되지 않은 것 | 근거 |
|---|---|
| 휴대폰 폭 화면 | 네 번의 AC와 critic 지적 어디에도 화면 폭이나 레이아웃이 없다. 앞서 D에서 발견했다던 잘림은 측정 착시였다(8절). 그러나 화면 폭이 검증 범위 밖이라는 점은 그대로다. |
| 외부 API 실제 호출 | D는 MockTransport로 검증했고 실제 MMCA 호출은 하지 않았다. 키 없이 띄웠다. |
| 명세 밖의 품질 | AC는 HTTP 응답과 문자열 검사 중심이다. 시각적 결과는 AC에 쓰이지 않으면 검증 대상이 아니다. |

## 6. mvpgen의 역할 후보(관찰에서 나온 가설)

| 역할 | 근거 | 확신 |
|---|---|---|
| 한 줄 아이디어를 AC가 있는 계약(`spec.json`)으로 바꾼다 | 네 실행 모두 5~9개 AC를 만들고 테스트가 AC와 1대 1이다 | 높음 |
| 계약 범위 안의 동작을 실제로 띄워 확인한다 | build critic이 서버를 띄워 curl로 AC를 하나씩 확인했다 | 높음 |
| 계약 밖의 결함은 잡지 못한다 | 화면 폭 같은 항목은 AC에 없어 검증되지 않는다. 결함이 실제로 통과한 사례는 확인하지 못했다(8절) | 낮음 |
| 요구에 없는 기능을 줄인다 | C에서 B의 두 기능이 빠졌다. 단 1회씩이고 D에는 요구와 무관한 feature가 남았다 | 낮음 |
| 반복 실수를 학습한다 | major 1건이 고쳐진 뒤 재발하지 않았지만 minor는 반복된다 | 낮음 |

## 7. 한계

- 실행이 4건이고 아이디어 세 종류에 같은 모델이다. 경향으로만 읽는다.
- 모델의 영향과 mvpgen의 영향이 분리되지 않았다. 같은 아이디어를 mvpgen 없이 모델에 직접 준 실행이 대조군으로 필요하다. 아직 없다.
- 테스트 수와 점수는 critic이 쓴 값이며 독립 검증하지 않았다.
- A의 코드 버전은 초기 커밋 이후의 어느 시점인지 실행 기록만으로 특정하지 않았다.

## 8. 정정: 휴대폰 잘림은 측정 착시였다

| 항목 | 내용 |
|---|---|
| 앞서의 주장 | D 앱이 휴대폰 폭(420px)에서 잘린다 |
| 측정 방법 | 헤드리스 Chrome `--window-size=420,...` 스크린샷 |
| 확인 결과 | 이 방식은 레이아웃 폭을 최소 500px로 잡고 스크린샷만 420px로 자른다(`innerWidth=500`). 대조군 앱도 같은 방식에서 똑같이 잘려 보였다 |
| 재측정 | 420px 폭 iframe 안에서 D와 대조군을 다시 찍었다. 둘 다 잘리지 않는다 |
| 영향 | "mvpgen이 놓친 결함"이라는 근거가 사라졌다. 이전 보고와 경과 보고 페이지(artifact)의 해당 서술은 정정이 필요하다 |

## 9. 대조군: mvpgen 없이 같은 아이디어를 모델에 직접 준 실행

조건: 아이디어 문장은 B, C와 같다. 파이프라인 지시 없이 Claude Code 서브에이전트(opus) 1회. 실행 환경과 비용 집계 방식이 달라 비용은 참고용이다.

| 항목 | 대조군 | B, C (mvpgen) |
|---|---|---|
| 스택 | 정적 HTML과 JS, 서버 없음, localStorage 저장 | FastAPI, SQLite |
| 산출물 | 3파일(index.html, logic.js, test_logic.js), 215줄 | 7~8파일, PRD와 spec.json 포함 |
| 명세 산출물 | 없음 | PRD.md, spec.json(AC 5~7개) |
| 기능 범위 | 요구 3가지, 정렬 3종(별점 높은순, 낮은순, 최근순), 읽음 전환, 삭제, 다크모드, 모바일 대응 | B: 읽음 표시, 삭제 포함. C: 입력 검증만 추가 |
| 테스트 | Node 단위 테스트(`node test_logic.js` 통과, 직접 재실행 확인). 화면 동작 테스트 없음 | pytest 5~7개(AC와 1대 1) |
| 검증 방식 | 자체 보고: 브라우저로 추가, 정렬, 개수, 삭제, XSS, 375px 확인 | Plan critic, build critic이 서버를 띄워 AC를 curl로 확인 |
| 휴대폰 폭 | 서브에이전트가 375px에서 확인했다고 보고. 내가 420px로 재측정해 잘리지 않음을 확인 | 확인 단계 없음. D 앱을 420px로 재측정하면 잘리지 않음 |
| 시간 | 129초 | 143~144초 |
| 확인하지 못한 것을 밝힘 | 다크모드, 실제 폰, 다른 브라우저를 명시 | critic 리뷰의 minor 지적 |

관찰:
- 대조군도 요구 3가지는 모두 충족했다. 단순한 아이디어에서는 mvpgen 없이도 결과가 동작했다.
- mvpgen이 더한 것은 앱의 기능이 아니라 산출물의 구조다: 서버 앱과 DB, 명세와 AC, AC와 연결된 테스트, 별도 critic의 검증 기록.
- 대조군은 스택을 스스로 정적 앱으로 골랐다. mvpgen은 같은 아이디어에 FastAPI와 SQLite를 골랐다. 이 차이는 mvpgen의 프롬프트(예: uv, 서버 실행과 smoke 규칙)가 스택을 정한다는 가설과 맞지만, 프롬프트를 읽어 확인하지는 않았다.
- 대조군은 요구에 없는 기능(낮은순 정렬, 다크모드)도 넣었다. 요구 밖 기능을 줄이는 효과가 mvpgen에 있다는 가설은 이 1회 비교로 지지되지 않는다.

한계: 대조군은 1회뿐이고 스택이 달라 기능과 품질을 직접 비교하기 어렵다. 같은 스택을 지정한 대조군은 하지 않았다.
