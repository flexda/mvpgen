1단계출발점

mvpgen이 만든 "오늘 뭐하지" 앱(FastAPI + Jinja2)은 화랑 전시는 CSV에서, MMCA 전시는 app/mmca.py로 API를 불러 data/mmca_cache.json에 저장해 읽는다. 다만 MMCA 부분은 실제 키로 한 번도 돌려 보지 않은 상태였다.

  • 엔드포인트: https://api.kcisa.kr/openapi/service/rest/moca/docMeta (문화데이터광장)
  • 키: secrets/mvp.env의 MMCA_SERVICE_KEY. 모든 실행에서 키 값은 출력하지 않았다.
  • 기존 코드: 100건씩 최대 10페이지, 즉 최대 1,000건만 받도록 되어 있었다.

2단계실제 API 첫 호출

3건만 요청해 응답 구조를 확인했다. HTTP 200, resultCode 0000, XML로 응답했다. 여기서 totalCount가 3,980건이라는 것을 확인했다. 기존 코드는 이 중 1,000건만 받는다.

이어서 앱의 fetch_all을 그대로 실행한 결과와 페이지 제한 없이 전부 받은 결과를 비교했다.

건수시간오늘 진행 중
기존 앱 (10페이지 제한)1,0002.1초54
전체3,9806.5초54

이번에는 진행 중 전시가 모두 앞쪽 1,000건 안에 있었지만, 응답이 날짜순이 아니어서 2026년 전시가 레코드 600번대에도 있었다. 페이지별 최대 종료일을 보면 1페이지는 2028년, 7페이지에서 다시 2026년이 나온다. 앞 몇 페이지만 받고 멈추는 방식은 안전하지 않다.

3단계날짜 필터 파라미터가 있는가

공식 문서(문화데이터광장 openapiView id=44)를 확인했다. 요청 파라미터는 다음 세 개뿐이다.

파라미터필수설명
serviceKey필수서비스 인증키
numOfRows선택페이지당 레코드 수
pageNo선택페이지 번호

결론

날짜·분류·장소로 거르는 파라미터는 없다. 문서에 없는 파라미터는 시험하지 않았다. 전부 받은 뒤 우리 쪽에서 걸러야 한다.

4단계1페이지 100건 살펴보기

규칙을 정하기 전에 numOfRows=100으로 한 번 호출해 데이터를 직접 살폈다.

관찰예시대응
subjectCategory가 맞지 않음같은 전시에 과거·현재·예정 세 값이 모두 붙음. 2025년에 끝난 "테스트"가 현재전시로 표시됨쓰지 않고 eventPeriod로 계산
같은 전시가 2~4번 중복"수련과 샹들리에" 4건중복 합치기
중복인데 제목이 조금씩 다름"데미안 허스트" / "데이미언 허스트", "이대원" / "이대원: 당신을…"장소+기간으로 묶고 가장 긴 제목 사용
같은 전시인데 기간이 다름"그래도 해보던 날들" 2026-08-30 / 2027-02-28 종료종료일이 가장 늦은 것만 남김
테스트 레코드제목이 "테스트"제외
요금 표기가 제각각0, 무료, -, 빈 값, 미정, 문장합칠 때 비어 있지 않은 값을 우선 사용. 정규화는 아직 안 함
필요 없는 필드creator·publisher·collectionDb는 모든 레코드가 같은 값, subDescription은 전부 빈 값저장하지 않음
장소는 관 이름만 있음서울·과천·청주·덕수궁·레지던시·해외·어린이미술관장소 필터 없이 전부 수집

5단계정제 규칙과 코드 변경

규칙내용
날짜종료일이 2026-08-01 이후인 전시. 8월 이후에 한 번이라도 열려 있던 전시가 남는다. 환경변수 MMCA_SINCE로 기준일을 바꿀 수 있다
장소거르지 않는다
1차 중복 합치기(장소, 시작일, 종료일)이 같으면 하나로 합친다. 제목은 가장 긴 것, 요금·참여자는 비어 있지 않은 첫 값
2차 중복 합치기합친 뒤에도 장소와 제목이 같으면 종료일이 가장 늦은 것만 남긴다
HTML 태그모든 값에서 <br/> 같은 태그를 지우고 공백을 정리한다
제외제목이 정확히 "테스트"인 레코드
기간 해석 불가버리지 않고 남겨 /review 화면에 보이게 한다

바뀐 파일

  • app/mmca.py: totalCount를 채우면 멈추고, 페이지 상한은 100으로 올렸다. clean_text, select_recent를 새로 만들었다.
  • app/main.py: 새로고침이 받기 → 거르기 → 저장 순서로 돈다. "전체 N건 중 M건 저장" 메시지를 보여 준다.
  • 테스트: 단위 테스트 5개 추가(경계일, 표기가 다른 중복, 테스트 레코드, 같은 제목 다른 기간, HTML 태그). AC3의 호출 횟수 기대값을 1회로 수정. 총 29개 통과.

버전 관리 안 됨

앱은 git에서 제외된 workspace/ 아래에 있어서 이 변경은 커밋되지 않았다.

7단계정기 수집 방법

서버가 켜져 있어도 수집은 버튼을 눌러야만 일어난다. 서버를 끄면 화면만 볼 수 없고 캐시 파일은 남는다. 정기 수집은 서버와 따로, 정해진 시각에 수집 코드를 실행해야 한다.

방법실행 위치특징
launchdMac예약 시각에 Mac이 잠자고 있었으면 깨어날 때 실행 (man launchd.plist로 확인)
cronMac예약 시각에 Mac이 잠자고 있으면 그 회차를 건너뜀
앱 안 스케줄러서버서버가 꺼지면 수집도 멈춤
GitHub ActionsGitHubMac이 필요 없음. 기본 브랜치에서만 돌고, 부하가 높을 때 늦어질 수 있음

결정

Mac은 쓰지 않는다. API 수집과 정제는 스크립트로, 화랑 정보는 크롤링으로 하고, 예약 실행은 GitHub Actions로 한다.

8단계적재 위치: Supabase

처음에는 데이터가 작아서 결과 파일을 GitHub 저장소에 커밋하는 방식을 권했다. 그런데 목표는 확장 가능한 구조를 만들면서 작은 데이터로 Supabase 스키마 같은 데이터 엔지니어링을 공부하는 것이다. 그래서 Supabase에 적재하기로 했다.

전체 흐름

flowchart LR
  A[GitHub Actions 예약 실행] --> B[collect_mmca.py]
  A --> C[crawl_galleries.py]
  B --> R1[(raw.mmca_snapshot)]
  C --> R2[(raw.gallery_extract)]
  R1 --> K[(core.exhibitions / core.venues / core.quality_issues)]
  R2 --> K
  K --> M[mart.v_exhibitions_on]
  M --> APP[앱]

항목내용영향

스키마 초안

raw

받은 그대로 쌓기만 한다. 수정하지 않는다.

  • ingest_runs (run_id, source, started_at, finished_at, status, api_total_count, row_count, error)
  • mmca_snapshot (run_id, payload_hash, payload jsonb)
  • gallery_extract (run_id, gallery_id, source_url, payload jsonb, needs_review)

core

정제된 층. 오늘 만든 규칙이 여기로 옮겨 온다.

  • venues (venue_id, source, name, branch, region)
  • exhibitions (exhibition_id, source_key, title, venue_id, start_date, end_date, charge_raw, is_free, artists text[], first_seen_at, last_seen_at)
  • quality_issues (run_id, source, record_ref, rule, detail)

mart

서비스용 조회. 앱은 이 층만 읽는다.

  • v_exhibitions_on(date)
  • v_new_this_week
